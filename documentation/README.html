1. Project Overview

This project is an implementation of the Cloud Resume Challenge, expanded into a practical AWS cloud engineering portfolio project. The objective was not simply to create an online resume, but to demonstrate how a modern cloud-based application can be designed, deployed, secured, documented and maintained.

The project combines a responsive resume frontend with AWS cloud services and a serverless visitor counter. The architecture uses Amazon S3, Amazon CloudFront, Amazon API Gateway, AWS Lambda and Amazon DynamoDB, with IAM used to control access.

Infrastructure-as-Code was introduced through AWS CloudFormation. Git and GitHub were used for version control and documentation, creating a foundation for future CI/CD and Terraform work.

Project Goal: Build a real cloud project that demonstrates practical AWS knowledge rather than relying exclusively on certification theory.

Architecture Flow

  1. A visitor requests the resume website.
  2. CloudFront receives and delivers the frontend content.
  3. The frontend is backed by files stored in Amazon S3.
  4. JavaScript sends a request to the API Gateway endpoint.
  5. API Gateway invokes the Lambda function.
  6. Lambda communicates with DynamoDB.
  7. DynamoDB stores and increments the visitor count.
  8. The response is returned through API Gateway to the browser.
  9. The visitor count is displayed on the resume.

6. Serverless Visitor Counter

One of the key requirements of the Cloud Resume Challenge was to implement a visitor counter. Rather than using a traditional application server, this project uses AWS serverless services.

Request Flow

Browser
    ↓
JavaScript fetch()
    ↓

    ↓

    ↓
DynamoDB
    ↓
Lambda response
    ↓
API Gateway
    ↓

JavaScript Integration

The frontend uses JavaScript to make a request to the API Gateway endpoint. The returned value is then displayed on the resume.

Lambda

The Lambda function was implemented using Python and the AWS SDK for Python, boto3. The function communicates with DynamoDB to retrieve and update the visitor count.

DynamoDB

DynamoDB provides the persistent storage layer for the visitor counter. This demonstrates the use of a managed NoSQL database without requiring the deployment or administration of database servers.

Testing: Visitor-count values increased during development and deployment testing, confirming that the frontend, API, Lambda and DynamoDB components were communicating successfully.

8. Infrastructure as Code — AWS CloudFormation

CloudFormation was introduced to move the project beyond manually configuring resources through the AWS Console.

The project contains an AWS directory with the CloudFormation template: 

AWS/template.yaml

CloudFormation Objectives

  • Define infrastructure using YAML.
  • Make infrastructure reproducible.
  • Keep infrastructure definitions inside Git.
  • Reduce dependence on manual configuration.
  • Build practical Infrastructure-as-Code experience.

Example Resource

Resources:

  ResumeBucket:
    Type: AWS::S3::Bucket
    DeletionPolicy: Retain
    UpdateReplacePolicy: Retain
    Properties:
      BucketName: !Ref BucketName

The S3 bucket resource was configured with retention policies so that infrastructure operations would not automatically remove the existing resume data.

Existing Resource Import

A particularly useful CloudFormation exercise involved importing the already-existing S3 bucket into the CloudFormation stack rather than deleting and recreating the bucket.

This provided practical exposure to managing existing AWS resources through Infrastructure-as-Code.

CloudFormation Validation

The AWS CLI was used to validate the CloudFormation template. 

aws cloudformation validate-template --template-body file://AWS/template.yaml --region af-south-1

The project uses the Cape Town AWS region: 

af-south-1

9. IAM and Security

Security is an important part of the project because the application uses several AWS services that communicate with one another.

Security Areas Considered

  • IAM permissions and least-privilege principles.
  • S3 access configuration.
  • CloudFront distribution access.
  • API Gateway CORS configuration.
  • Lambda permissions.
  • DynamoDB permissions.
  • CloudFormation resource management.
  • AWS account and CLI credentials.

S3 Public Access

Public access controls were explicitly considered when configuring the S3 infrastructure. The CloudFormation template was updated to include public-access-block configuration as part of the security approach.

CORS

The visitor counter initially encountered a browser CORS issue. API Gateway CORS configuration was updated so that browser requests could successfully communicate with the backend API.

Security lesson: Cloud architecture is not simply about making resources work. Permissions, access paths, CORS and resource exposure must be considered as part of the design.

12. Troubleshooting and Problems Solved

One of the most valuable parts of the project was the troubleshooting process. Several issues occurred during development and deployment, providing practical experience that cannot be gained from theory alone.

AWS CLI Authentication and Region Problems

AWS CLI commands initially produced authentication and token-related errors, including errors involving invalid credentials and request signing.

The underlying issue was related to the AWS region configuration. The Cape Town region, af-south-1, had to be enabled in the AWS account before the project could operate correctly there.

CloudFormation Validation

CloudFormation initially produced deployment and rollback problems. Stack events were used to identify validation failures instead of attempting to guess the cause. 

aws cloudformation validate-template --template-body file://AWS/template.yaml --region af-south-1

aws cloudformation describe-stack-events --stack-name YOUR_STACK_NAME --region af-south-1

aws cloudformation describe-stack-resources --stack-name YOUR_STACK_NAME --region af-south-1

CloudFormation Rollback

A CloudFormation deployment entered a rollback state. Instead of abandoning the infrastructure work, stack events were examined, the template was corrected and the existing S3 bucket was ultimately imported into the stack.

CORS Error

The browser initially rejected the API request because of CORS. API Gateway was configured to permit the browser request, resolving the communication issue.

CloudFront Caching

Another important issue occurred when changes to JavaScript were not immediately visible after deployment.

The browser and CloudFront were both capable of serving cached versions of the files. Browser developer tools and cache controls were used to confirm whether the latest version of the JavaScript had actually been loaded.

Key lesson: When a cloud application appears not to have updated, the problem may be caching rather than the deployment itself.

Favicon 403

A favicon request also returned a 403 response during testing. This demonstrated the importance of examining individual browser network requests rather than assuming that every request has the same cause.

17. Key Lessons Learned

1. Cloud architecture is interconnected

A seemingly simple website can involve several services. A problem in one layer can affect another layer, which makes understanding the complete request path important.

2. Infrastructure as Code changes how infrastructure is managed

CloudFormation provided practical experience with defining and managing infrastructure through code rather than relying entirely on the AWS Console.

3. Troubleshooting is a core cloud skill

Authentication problems, region configuration, CloudFormation rollback events, CORS errors and caching problems demonstrated the importance of methodical troubleshooting.

4. Serverless architecture can provide significant functionality

The visitor counter did not require a traditional server. API Gateway, Lambda and DynamoDB were sufficient to provide a functional backend.

5. Security must be considered from the beginning

IAM permissions, S3 access controls, CORS and service-to-service permissions all form part of the application's security posture.

6. Documentation is part of the project

A professional cloud project should explain not only what was deployed, but why it was designed that way and what problems were encountered along the way.
